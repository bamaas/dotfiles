# `examples/` directory guide

Real `.gitlab-ci.yml` files generated by the [gitlab-ci-skill](../) against well-known OSS projects. Use them as a reference for what idiomatic GitLab CI/CD pipelines look like across stacks, or as a sanity check when authoring your own.

## How to read these examples

Each subdirectory is one stack. Each subdirectory contains:

- One or more `.gitlab-ci*.yml` files: the skill's actual generated output, captured from a fresh-session run.
- A `README.md`: provenance (which upstream project the YAML was generated from), the patterns the YAML demonstrates, and reproduction commands.

No upstream source code is redistributed by this repo. The YAML stands alone.

| Directory | Stack | Source |
|---|---|---|
| [`node-mocha/`](node-mocha/) | Node + Mocha + nyc, no committed lockfile | [`expressjs/cors`](https://github.com/expressjs/cors) |
| [`python-uv-tox/`](python-uv-tox/) | Python + uv + tox + parallel matrix; full W1/W2/W3/W4 narrative | [`pallets/markupsafe`](https://github.com/pallets/markupsafe) |
| [`python-click/`](python-click/) | Python + uv + tox-driven `.tox` extends + schedule-gated matrix | [`pallets/click`](https://github.com/pallets/click) |

More stacks (Go, Ruby, Docker, Rust) are planned per the engineering tracking issue. See "How to contribute" below.

## How to use them

Three ways:

1. **Read the YAML.** Each file is a working `.gitlab-ci.yml` you can drop into a project of the matching stack and adapt. The patterns the skill applies (default block, hidden-job + extends, lockfile cache, schedule-gated matrix, Catalog include) are idiomatic GitLab shapes; copying them by hand is fine.

2. **Reproduce it.** Each stack's `README.md` carries the reproduction commands: clone the named upstream into `/tmp/`, run the skill in a fresh AI editor session, compare the agent's output to the committed YAML. Differences are expected for component versions and comments; the shape should match.

3. **Validate locally.** From the repo root:

   ```bash
   bash scripts/verify.sh -f examples/<stack>/.gitlab-ci.yml lint
   bash scripts/verify.sh -f examples/<stack>/.gitlab-ci.yml show
   ```

   `lint` and `show` work against the committed YAML alone, without cloning the upstream. The `lint-examples` CI gate runs the same lint check on every push.

## How to contribute a new example

Four steps:

1. **Pick a real OSS project** in a stack the skill should demonstrate. Smaller is better (faster lint, less ambiguity). The project should have no existing `.gitlab-ci.yml`, or you should reset to a no-CI state by cloning to `/tmp/` and removing the CI directories:

   ```bash
   git clone <github-url> /tmp/<name>
   cd /tmp/<name>
   rm -rf .gitlab-ci.yml .gitlab .github/workflows .git
   git init -q && git add . && git commit -q -m init
   ```

2. **Run the skill from a fresh AI editor session.** Prompt:

   > Set up GitLab CI for this repo.

   Capture the agent's output to `examples/<stack>/.gitlab-ci.yml`. Do not hand-tune the YAML; the value of the example is that it's actual skill output.

3. **Write `examples/<stack>/README.md`** following the pattern of the existing READMEs in this directory:
   - The source link to the upstream project.
   - 3 to 5 bullets naming the idiomatic patterns the YAML demonstrates.
   - Reproduction commands.

4. **Push the MR.** CI runs three gates:
   - `validate-skill`: the agentskills.io spec.
   - `lint-examples`: `glci lint` against every `.gitlab-ci*.yml` under `examples/`.
   - `verify-examples-shape`: only `.gitlab-ci*.yml` and `README.md` allowed under each example directory; no nested subdirs.

   All three must pass.

If your example genuinely needs files beyond the YAML and the README (it almost certainly doesn't), open an issue first. We're deliberate about shipping the smallest disk footprint possible.
